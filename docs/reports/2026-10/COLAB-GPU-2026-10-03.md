## Résultat livré

`src/compute/colab-runner.ts` lance des scripts Python sur une VM éphémère, installe
les dépendances explicitement déclarées, transmet les entrées contrôlées et
rapatrie les sorties. L4 par défaut, A100 explicite ; H100 se replie sur A100 après
refus d'allocation, d'habilitation ou HTTP 503. La VM est arrêtée en `finally` avec
vérification côté serveur, sur succès, erreur, délai et signal interceptable.
Une fermeture non confirmée est une erreur visible et bloque un nouveau job.

Le compteur persistant utilise `writeJsonAtomic`, un verrou excluant les jobs
concurrents, des réservations avant allocation et un refus sur état corrompu.
Le plafond journalier vaut 50, configurable par
`CODEBUDDY_COLAB_MAX_UNITS_PER_DAY`. La réservation prudente utilise le délai du
job, 240 secondes de marge et un plafond horaire par GPU. Une mesure manquante
ne remet pas la charge à zéro. Le jour est UTC ; un job franchissant minuit est
refusé. Voir [le guide](../../colab-gpu.md) pour les détails et la récupération.

`colab_run` est défini, enregistré dans la fabrique de recherche et indexé dans
les métadonnées. Il exige confirmation et déclare un effet `emission`, sans
exposition aux pairs (`fleetSafe: false`). L'étape d'exécution de « Adding a Tool »
passe par la délégation existante `CodeBuddyAgent.executeTool` → `ToolHandler` →
registre formel : aucun dispatch parallèle ne contourne la confirmation.
Deux tests du vrai ToolHandler prouvent refus sans allocation et exécution après
confirmation, avec transmission du signal d'annulation.

CLI : `buddy colab run <script.py> --gpu L4|A100|H100 --in ... --out ...`,
`--dependency`, `--timeout`, `buddy colab status`, `buddy colab stop <cb-session>`.
L'opt-in est `CODEBUDDY_COLAB=true`. Sans lui, le nom `colab` conserve son alias
historique vers `autonomy`. Les aides et le catalogue sans opt-in sont identiques
à la base octet pour octet (captures avant/après et SHA-256 conservés).

## Confidentialité et documentation préalable

Lecture entière de `colab readme` et des aides new, exec, install, download,
drivemount, ls, log, stop, upload, sessions, usage et status avant toute écriture.
Tous les appels réels utilisent `--auth oauth2`. Aucun montage Drive.
Les fichiers du dossier d'authentification n'ont été ni lus par l'agent, ni
copiés, ni affichés, ni commis. Seule la CLI autorisée utilise son état OAuth.

Les chemins lexicaux et canoniques doivent rester dans le projet. Noms sensibles,
liens durs, fichiers spéciaux et contenus reconnus par les détecteurs existants
sont refusés, indépendamment de l'override de lecture locale. Les octets contrôlés
sont figés dans des copies temporaires privées. Aucun environnement local n'est
transmis au kernel. Les dépendances sont des noms PyPI ou versions épinglées,
sans URL ni options pip. Les sorties sont également contrôlées, limitées et
écrites dans un dossier nouveau sans remplacement d'un livrable existant.

Profil Code Buddy temporaire ; état OAuth Colab existant utilisé uniquement via
la CLI. Budget de recette fixé à 15 unités. Six allocations L4, toutes fermées :

| Cas | Résultat utilisateur | Preuve après fermeture |
|---|---|---|

Le défaut de marqueur a été corrigé : une inclusion dans un traceback ne vaut
plus réussite. Le test reproduit stderr contenant la ligne de code avec le
marqueur, alors que la CLI rend 0. La capture d'erreur inclut désormais stderr.

Modèle ouvert : [Google ddpm-cat-256](https://huggingface.co/google/ddpm-cat-256),
licence Apache-2.0 déclarée dans la fiche et confirmée dans les métadonnées de son
API, révision `82ca0d5db4a5ec6ff0e9be8d86852490bc18a3d9`, environ 114 M paramètres.
Les quatre fichiers ont été ouverts pour inspection visuelle et copiés dans le
partage avec empreintes. Il s'agit d'aperçus de test pour une galerie : la qualité
est variable, avec des déformations visibles, pas d'images finales de publication.

## Ce que je n'ai pas pu vérifier

- Consommation définitivement débitée par Google : seul le solde CLI inchangé,
  le débit instantané et la charge prudente sont observables dans cette recette.
- A100 et H100 réels, ainsi que leur repli en capacité : vérifiés par injection,
  y compris HTTP 503, sans allocation de ces GPU pour préserver le budget.
- Windows et macOS ; la CLI Colab officielle annonce Linux/macOS, pas Windows.
- SIGINT/SIGTERM sur VM réelle et panne réseau durable : signaux et annulation
  testés sans réseau ; le délai et l'erreur Python ont été éprouvés réellement.
- Arrêt non interceptable (SIGKILL, panne hôte) : aucun finally ne peut s'exécuter ;
  récupération explicite nécessaire, état conservateur bloquant. Une identité de
  VM perdue pendant une allocation CLI tuée ne peut pas être détruite par son nom
  sans récupération par la CLI officielle ; le runner signale l'absence de preuve.
- Choix autonome de colab_run par un LLM, entraînement, ComfyUI et vision : hors
  des quatre jobs demandés ; le dispatch et la confirmation ont été exécutés dans
  le vrai ToolHandler, avec le calcul remplacé dans ces tests uniquement.
- Paquet installé/reconstruit et suite intégrale du dépôt : recette CLI depuis
  les sources tsx, typecheck complet et suites ciblées exécutés.

Les captures, les quatre PNG, les compteurs et le rapport destiné à l'utilisateur
sont dans le dossier de livraison partagé indiqué dans la mission. Aucun service
nouveau ni tâche de fond laissés actifs. Aucun push.
