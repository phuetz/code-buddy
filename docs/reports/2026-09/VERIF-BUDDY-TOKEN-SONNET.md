## Bilan (10 lignes)

Le CLI `buddy token` ne journalise ni n'affiche jamais `JWT_SECRET` (seul le JWT généré, qui est la sortie voulue, apparaît). Résolution `--env` → variable d'env → `~/.codebuddy/server.env` correctement gardée : fichier absent, illisible ou sans secret refuse proprement en exit 2, `--days` est borné `[1,365]` avec rejet net de `0`, négatifs, `366` et non-entiers (vérifié en live pour tous les cas, dont un seul unitairement testé). `--role admin` n'ajoute aucune barrière au-delà de posséder le secret serveur, ce qui est acceptable pour un outil d'exploitant local. Les scopes du rôle `user` (`chat, chat:stream, sessions, tools`) sont cohérents avec `src/server/websocket/handler.ts` : authentification WS et appel HTTP confirmés en live avec un jeton frais. Côté PWA, `consumeHashToken()` capture, stocke en `sessionStorage` (jamais `localStorage`), efface le hash via `history.replaceState` avant tout `connectWs()`, et le jeton ne transite qu'en payload JSON du message `authenticate` — jamais en URL/Referer ; test DOM présent, `sw.js` bien incrémenté en v5, comportement confirmé en direct via Playwright (écran de chat sans formulaire, hash vide). Telegram n'envoie qu'au `chat_id` configuré, inclut l'avertissement d'expiration, et le chemin d'erreur (config absente ou réseau) laisse le jeton affiché localement avec un exit non nul. Suite complète (`tests/commands`, `tests/server`, `donnees-personnelles`) : 2055 tests verts, 0 rouge ; tsc, eslint, `node --check`, `git diff --check` tous à 0. Deux trous de test unitaire mineurs et sans impact observé : le hash malformé et l'échec réseau Telegram ne sont vérifiés que par lecture de code (comportement sûr par construction : `try/catch` systématiques). Aucun correctif n'a été nécessaire.

VERDICT: PUSHABLE
