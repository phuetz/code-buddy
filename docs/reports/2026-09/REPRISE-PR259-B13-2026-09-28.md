# PR #259 — reprise de la revue n°14, cible 2.3.1

Branche `fix/securite-2-3-0`, tête relue `d9559e6d1`. La relecture indépendante n°14 et la mission ont été lues en entier. Toutes les reproductions utilisent `HOME` et `USERPROFILE` isolés sous `_qa/securite-reprise-14`, deux dépôts Git factices et des jetons `FAKE-*`. Aucun identifiant réel du propriétaire n'a été ouvert. Aucun push ni tâche de fond.

## Bloquant → traitement → preuve

| Bloquant ou réserve | Traitement | Preuve |
| --- | --- | --- |
| **B13 — `execute_code` lisait `~/.codebuddy/codex-auth.json` depuis un dépôt propre ou protégé et rendait le jeton en clair.** | L'outil exposé au modèle impose `envMode: 'isolate'` et `confinement: 'compute'`, même si son constructeur reçoit d'autres options. Le confinement Landlock/seccomp ne donne au sous-processus que le répertoire d'exécution jetable ; si le noyau ne peut le fournir, le code utilisateur ne démarre pas. `HOME`/`USERPROFILE` fabriqués ne constituent pas la seule barrière : un chemin absolu et un HOME fourni dans les arguments sont également refusés par le noyau. | Nouveau `reprise-14-execute-code.test.ts` via le vrai registre : **4/4 rouges avant** (JavaScript, Python, shell et dépôt à `.env` suivi, faux OAuth en clair) ; **verts après**. Test supplémentaire du chemin absolu avec HOME réinjecté vert. L'intégration réelle `execute-code-real.test.ts` passe **3/3** sur Linux. |
| **Usage légitime de `execute_code` et changement de défaut.** | JavaScript, Python et shell restent disponibles dans la vue confinée ; TypeScript est transpilé par le parent puis exécuté comme JavaScript confiné. Sur Windows/macOS ou Linux sans Landlock/seccomp, l'outil refuse l'exécution. Le canal optionnel code→outil RPC est inactif pour cet outil confiné. Le contrat du runner interne `executeCode` avec options explicites reste séparé. Le changement est documenté dans `CHANGELOG.md`, `CLAUDE.md` et la définition de l'outil. | Calculs JavaScript et TypeScript `6 × 7 = 42` verts sur ce Linux ; test d'intégration réel vert ; les assertions Windows/macOS de l'intégration exigent le refus explicite. Les tests RPC du runner interne restent **verts**. |
| **Réserve dépôt frère :** `g\\it -C ../protected show` échappait au détecteur Git lorsque le répertoire courant était propre et dépendait du confinement noyau. | La détection de l'exécutable Git applique la règle lexicale POSIX de suppression des caractères d'échappement à toute la ligne, en gardant aussi la reconnaissance brute des chemins Windows. Une invocation Git que le parseur ne peut prouver sûre est refusée avant le shell. | **3/3 rouges avant** sur `g\\it`, `\\g\\i\\t`, `env g\\it` ; **verts après**. Le vrai `BashTool` renvoie `Git invocation could not be checked`, avant tout recours au bac à sable natif. |
| **Réserve de performance et de disponibilité :** parcours répété de l'arbre, 100 000 dossiers / 64 dépôts maximum. | Constat accepté, **pas présenté comme corrigé**. La revue mesure 6,5 s à froid et ~0,5 s par résultat chaud sur son dépôt ; le code retient la sortie et refuse le shell si l'inventaire est incomplet. Un cache fondé seulement sur l'heure du répertoire pourrait manquer un dépôt nouvellement créé, surtout sur un système de fichiers à horodatage grossier ; il n'a pas été ajouté. Le coût et les limites restent explicitement documentés pour la décision 2.3.1. | Lecture du parcours et des deux seuils dans `tracked-git-output-redactor.ts` et `git-secret-process-boundary.ts` ; tests de sécurité verts. Aucune mesure de performance indépendante sur un grand monorepo n'a été faite durant cette reprise. |

## Vérifications

- `npm test -- tests/security --configLoader runner` : **75 fichiers, 1 493 tests verts**.
- Tests voisins `execute-code-tool-rpc`, validateur Bash, reprise B12 : **4 fichiers, 102 tests verts**.
- `RUN_REAL_TESTS=1 npm test -- tests/tools/execute-code-real.test.ts --configLoader runner` : **3 tests verts** sur Linux.
- `npx vitest run tests/security/donnees-personnelles.test.ts --configLoader runner` : **40 tests verts**.
- `npx tsc --noEmit`, ESLint ciblé et `git diff --check` : **sortie 0**.
- Correctifs et régressions commités en `a3d65606c` (`fix(security): confiner execute_code et reconnaître Git échappé`).
- `--configLoader runner` est requis ici parce que le `node_modules` lié est en lecture seule pour le bac d'exécution ; le chargeur Vitest par défaut échoue avec `EROFS` avant les tests.

La cible de cette PR est **2.3.1** selon le pilote. B13 et le chemin Git frère sont fermés dans les chemins testés. La réserve de performance, la CI Windows et l'audit exhaustif des autres lanceurs restent des limites de la déclaration de sécurité générale ; ce rapport ne prétend pas à une garantie universelle sur tous les processus du produit.

## Ce que je n'ai pas pu vérifier

- Windows, macOS et un Linux dépourvu de Landlock/seccomp n'ont pas été exécutés localement ; le refus y est vérifié par le code et par des assertions portables, pas par une CI native de cette tête.
- La suite complète du dépôt, un vrai modèle, Ink, Electron/Cowork et une flotte distante n'ont pas été lancés. Le vrai registre et le vrai `BashTool` ont été exercés avec des dépôts et identifiants factices.
- L'inventaire sur un monorepo de plus de 100 000 dossiers ou 64 dépôts, ainsi que son impact de latence en production, n'a pas été mesuré ici. La réserve de performance n'est pas levée.
- Les lanceurs de processus autres que ceux cités par la revue n'ont pas tous été audités. Le runner interne `executeCode` peut encore hériter de l'environnement lorsqu'un appelant de confiance le demande explicitement ; cette reprise ferme l'outil `execute_code` exposé au modèle.
